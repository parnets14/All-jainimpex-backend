# Open-session state across HRMS break displays

The follow-up exposes `hasOpenSession` and `completedSessionCount` from the shared attendance calculator and uses the open-state flag in all three HRMS tables. Working Time resolves configured lunch from report-level metadata or a day fallback, while Attendance and Attendance Master show `Not applicable` when break metadata is absent. The display metadata does not change credited-time formulas, but the new legacy-open assertion contradicts the retained stored-hours compatibility path and fails at runtime. The API also omits `hasOpenSession` from JSON for some non-open calculated rows because the calculator can return `undefined` instead of `false`.

Watch for: **confirmed (P1)** the executable simulation fails because its legacy-open fixture expects zero credit while production preserves 480 stored minutes; **confirmed (P2)** `hasOpenSession` is not consistently serialized as a boolean.

**Verdict**: NEEDS_CHANGES

## High-level view

Modern open-only sessions, completed sessions followed by an open session, and no-session legacy `punchIn` without `punchOut` now produce pending state. Attendance and working-time responses forward it, and each UI uses it directly for `Punch-out pending`.

Working Time reads lunch configuration from the report first and then from a day with metadata, displaying an em dash when neither exists. Attendance and Attendance Master avoid manufacturing a configured zero when calculation metadata is absent.

The metadata additions do not feed payroll calculations. The legacy-open fixture nevertheless expects stored-hours credit to change from 480 to zero, so the executable check aborts before its trailing-open, gap, overlap, and settings assertions complete.

## Legacy-open assertion conflicts with the compatibility fallback

The new fixture contains `punchIn` and `workingHours: 8` but no `sessions` or `punchOut`, then asserts zero credited minutes (`crm_backend/scripts/simulateHalfDayScenarios.mjs:173-179`). `calculateAttendanceTime` marks the row open, but its no-session compatibility path still accepts positive stored hours, returning 480 credited minutes with `source: "stored-hours-only"`. This is **confirmed (P1)** by `node crm_backend/scripts/simulateHalfDayScenarios.mjs`, which exits at line 177 with `480 !== 0`.

Changing the calculator to satisfy this assertion would change payroll inputs for legacy open rows, contrary to the requirement that canonical payroll math remain unchanged. Preserve the stored-hours expectation and assert `hasOpenSession: true`, or explicitly approve and implement the payroll behavior change if zero credit is intended.

## Open-state serialization is not boolean-stable

The legacy branch builds `hasOpenSession` with an `&&` chain (`crm_backend/utils/attendanceTime.js:31-34`). When a calculated record has neither sessions nor `punchIn`, the expression evaluates to `undefined`; JSON then removes the field forwarded by the attendance and working-time serializers (`crm_backend/routes/attendanceRoutes.js:95-96`, `crm_backend/controllers/hrmsController.js:411-412`). This is **confirmed (P2)** for stored-hours-only Present rows and empty calculated records: `completedSessionCount` remains zero, but `hasOpenSession` is absent rather than `false`.

Normalize the expression with `Boolean(...)` so the API surface is consistently `true` or `false`. The current UIs tolerate omission because it is falsy, but other clients should not receive a shape-dependent contract.
