## Audit 1 — N+1 Loop Writes

### Summary

10 files were found that perform individual INSERT / UPDATE calls inside `for...of` / `forEach` loops instead of using `insertMany`, `bulkWrite`, or `updateMany`. 6 files already use correct batch patterns. Scripts are the most severe offenders (run across thousands of documents). Several cron jobs also run N+1 per employee on every scheduled tick.

---

### 🔴 CRITICAL

#### 1. `scripts/resyncInvoiceTotals.js` — `resyncInvoices()`
- **Lines**: 61–217
- **Pattern**: Outer loop over all invoices → inner loop per item → `Product.findById()` per item (N reads) → second inner loop → another `Product.findById()` per item → `invoice.save()` (N writes)
- **Problem**: For 500 invoices with 10 items each = **10,000 individual product reads + 500 saves**. No transaction wrapping.
- **Fix**: Pre-load all required products with a single `Product.find({ _id: { $in: allProductIds } })` before the outer loop, build a Map, then collect all invoice mutations and flush with `bulkWrite` at the end.

```js
// ❌ CURRENT
for (const invoice of invoices) {
  for (const item of invoice.items) {
    const product = await Product.findById(item.product).lean(); // N×M reads
  }
  await liveInvoice.save(); // N writes
}

// ✅ FIX
const allIds = [...new Set(invoices.flatMap(inv => inv.items.map(i => i.product.toString())))];
const productMap = new Map((await Product.find({ _id: { $in: allIds } }).lean()).map(p => [p._id.toString(), p]));

const bulkOps = [];
for (const invoice of invoices) {
  // use productMap instead of individual find()
  bulkOps.push({ updateOne: { filter: { _id: invoice._id }, update: { $set: { ... } } } });
}
if (bulkOps.length) await Invoice.bulkWrite(bulkOps, { ordered: false });
```

#### 2. `scripts/migrateHistoricalAccounting.js` — `migrateDealerInvoices()`, `migrateSupplierInvoices()`, `migrateDealerPayments()`, `migrateSupplierPayments()`
- **Lines**: 80–107, 135–162, 190–227, 255–292
- **Pattern**: Loop over all records → `JournalVoucher.findOne()` per record (N reads) → `createXxxEntry()` per record (N writes)
- **Problem**: 4 separate functions with the identical anti-pattern. For 1,000 invoices = **2,000 individual DB round trips** before migration is complete.
- **Fix**: Extract all reference IDs upfront, run a single `JournalVoucher.find({ referenceId: { $in: ids } })` to get existing entries, build a Set of already-migrated IDs, then collect new journal docs and flush with `insertMany` in chunks of 500.

```js
// ❌ CURRENT
for (const invoice of approvedInvoices) {
  const existing = await JournalVoucher.findOne({ referenceId: invoice._id }); // N reads
  if (!existing) {
    await createDealerInvoiceEntry(invoice, ...); // N writes
  }
}

// ✅ FIX
const ids = approvedInvoices.map(i => i._id);
const existing = await JournalVoucher.find({ referenceType: 'DealerInvoice', referenceId: { $in: ids } }).select('referenceId').lean();
const migratedSet = new Set(existing.map(e => e.referenceId.toString()));

const docs = approvedInvoices
  .filter(inv => !migratedSet.has(inv._id.toString()))
  .map(inv => buildDealerInvoiceJournalDoc(inv));

// Chunk to avoid oversized statement
for (let i = 0; i < docs.length; i += 500) {
  await JournalVoucher.insertMany(docs.slice(i, i + 500), { ordered: false });
}
```

## Audit 2 — External Dependency Cascade Failures

### Summary

The backend has **7 external integration points** with **zero circuit breakers** and **zero explicit timeouts on network calls**. A slowdown or outage at any of these services will cause all concurrent requests to that code path to queue, exhaust async resources, and visibly degrade unrelated parts of the app.

No packages found: ❌ `opossum` ❌ `cockatiel` ❌ `axios-retry` ❌ `p-retry`

---

### 🔴 HIGH

#### 1. Firebase Realtime Database — Admin Notification Writes (`services/adminNotificationService.js`)
- **Lines**: 34–61
- **Call**: `await db.ref('/notifications/...').push(notif)`
- **Timeout**: ❌ None
- **Error handling**: ⚠️ **Silent `catch (e) {}`** — failures are completely invisible
- **Cascade scenario**: Firebase RTDB outage → every order creation, credit limit event, delivery failure, and employee no-show triggers a hanging RTDB write that silently fails. Admins lose all real-time visibility with no indication anything is wrong.
- **Fix**:
  - Wrap in `Promise.race([write, timeout(3000)])` — fail fast after 3 seconds
  - Replace silent catch with structured logging: `logger.warn('adminNotification failed', { company, type, err })`
  - Optionally add `opossum` circuit breaker: after 5 failures in 10 seconds, open circuit for 30 seconds

```js
// ❌ CURRENT
try {
  await db.ref(`/notifications/${c}`).push(notif);
} catch (e) { /* silent */ }

// ✅ FIX
const writeWithTimeout = Promise.race([
  db.ref(`/notifications/${c}`).push(notif),
  new Promise((_, reject) => setTimeout(() => reject(new Error('RTDB timeout')), 3000))
]);
try {
  await writeWithTimeout;
} catch (err) {
  console.warn(`[adminNotification] Failed for company ${c}:`, err.message);
  // Circuit breaker trips here; unrelated request paths continue unaffected
}
```

---

### 🟡 MEDIUM

#### 2. Firebase Cloud Messaging — Push Notifications (`services/firebaseNotificationService.js`)
- **Line**: 83 — `await admin.messaging().send(message)`
- **Timeout**: ❌ None (Firebase Admin SDK default: 10s, but not configurable here)
- **Error handling**: ✅ Basic — returns `{ success: false }`, invalid tokens cleared
- **Cascade scenario**: FCM quota exceeded or service degraded → every invoice, order, delivery status change blocks waiting for FCM for up to 10 seconds per notification call
- **Fix**: Fire-and-forget pattern for non-critical notifications; wrap in `setTimeout` fallback. For critical notifications, add `Promise.race` with 5 s timeout.

#### 3. Google Routes API (`DeliveryExecutiveAppBackend/controllers/assignmentController.js`)
- **Lines**: 1030–1066
- **Call**: `await fetch('https://routes.googleapis.com/directions/v2:computeRoutes', {...})`
- **Timeout**: ❌ **None** — `fetch()` with no `AbortController` will hang indefinitely if network drops
- **Error handling**: ✅ Falls back to nearest-neighbor algorithm — good
- **Cascade scenario**: Google API latency spike → delivery assignment endpoint hangs for 60+ seconds; multiple concurrent assignment requests could exhaust Node event loop queue
- **Fix**: Add `AbortController` with 5 s timeout (fallback is already coded, just ensure it triggers)

```js
// ❌ CURRENT
const response = await fetch('https://routes.googleapis.com/...', { ... });

// ✅ FIX
const controller = new AbortController();
const tid = setTimeout(() => controller.abort(), 5000);
try {
  const response = await fetch('https://routes.googleapis.com/...', {
    signal: controller.signal, ...
  });
  clearTimeout(tid);
} catch (err) {
  clearTimeout(tid);
  // Existing nearest-neighbor fallback runs here ✅
}
```

#### 4. Nodemailer SMTP (`controllers/dealerLedgerController.js`)
- **Lines**: 939–1000
- **Call**: `await transporter.sendMail(mailOptions)`
- **Timeout**: ❌ No `connectionTimeout`, `socketTimeout`, or `greetingTimeout` on the transporter
- **Cascade scenario**: SMTP server slow to respond → ledger statement email endpoint blocks for 2+ minutes until TCP timeout fires; user gets a spinner indefinitely
- **Fix**: Add timeouts to transporter creation and decouple email sends from the HTTP response

```js
// ❌ CURRENT
const transporter = nodemailer.createTransport({
  host: process.env.EMAIL_HOST,
  port: process.env.EMAIL_PORT,
  // No timeouts
});

// ✅ FIX
const transporter = nodemailer.createTransport({
  host: process.env.EMAIL_HOST,
  port: process.env.EMAIL_PORT,
  connectionTimeout: 5000,   // 5s to establish TCP connection
  greetingTimeout: 5000,     // 5s for SMTP EHLO greeting
  socketTimeout: 10000,      // 10s per socket operation
});
```

#### 5. Firebase RTDB — Trail History Reads (`cron/seDailySummary.js`)
- **Line**: 118 — `await firebaseDB.ref(...).once('value')`
- **Timeout**: ❌ None
- **Error handling**: ✅ Catch falls back to zero stats — acceptable
- **Fix**: Add `Promise.race` with 5 s timeout; cron continues with zero stats as fallback (already coded)

#### 6. MongoDB / Mongoose (`config/multiDatabase.js`)
- **Current**: `serverSelectionTimeoutMS: 5000`, `socketTimeoutMS: 45000`
- **Issue**: 5 second server selection is aggressive under load; 3 company connections can fail independently adding up to 15 seconds of wait time in parallel startup
- **Improvement**: Add `heartbeatFrequencyMS: 10000` and `maxConnecting: 2` to avoid thundering-herd reconnects

#### 7. Redis / ioredis (`config/redis.js`)
- **Current**: `maxRetriesPerRequest: 3`, `retryDelayOnFailover: 100`
- **Issue**: 3 retries at flat 100ms = 400ms total retry budget; no exponential backoff; no `connectTimeout`
- **Improvement**: Use `retryStrategy` with exponential backoff capped at 2 s

```js
// ✅ Better retry strategy
retryStrategy: (times) => Math.min(100 * Math.pow(2, times), 2000)
```

### No Circuit Breakers Detected

**Recommendation**: Install `opossum` (the most maintained Node.js circuit breaker):

```bash
npm install opossum
```

Priority wrapping order:
1. Firebase RTDB writes (admin notifications) — highest business impact
2. FCM push sends — high volume, silently fails already
3. Google Routes API — network fetch without timeout
4. Nodemailer — blocks HTTP response thread

Pattern:
```js
import CircuitBreaker from 'opossum';

const options = { timeout: 5000, errorThresholdPercentage: 50, resetTimeout: 30000 };
const breaker = new CircuitBreaker(adminNotificationService.send, options);
breaker.fallback(() => console.warn('Admin notification circuit open — skipping'));
breaker.on('open', () => console.error('🔴 Admin notification circuit OPEN'));
breaker.on('halfOpen', () => console.info('🟡 Admin notification circuit HALF-OPEN'));
breaker.on('close', () => console.info('🟢 Admin notification circuit CLOSED'));
```

## Audit 3 — Optimistic UI Updates

### Summary

**100% of user-facing mutation operations** (create, update, delete, status toggle) use a strict **wait-for-server-then-update** pattern. No optimistic updates exist anywhere in the frontend. The UX effect: every click produces a visible loading spinner and a frozen UI until the server (hosted on Render.com, with cold-start latency) responds — typically 200–2000 ms.

---

### 🔴 HIGH PRIORITY — Quick Wins

#### A. Delete Operations (14 affected components)

Current pattern found uniformly across all delete handlers:

```js
// ❌ CURRENT — waits for server, then updates UI
const handleDelete = async (id) => {
  setLoading(true);
  const response = await apiService.deleteItem(id);   // ← UI frozen here
  if (response.success) {
    fetchAllItems();   // full refetch after server confirms
  }
  setLoading(false);
};
```

Optimistic pattern to apply:

```js
// ✅ OPTIMISTIC — UI updates immediately, rolls back on failure
const handleDelete = async (id) => {
  const previous = [...items];                         // snapshot for rollback
  setItems(prev => prev.filter(i => i._id !== id));   // ← instant UI update

  try {
    await apiService.deleteItem(id);
  } catch (err) {
    setItems(previous);                                // ← rollback on error
    toast.error(`Delete failed: ${err.message}. Changes reverted.`);
  }
};
```

### 🟡 MEDIUM PRIORITY

#### C. Form Submissions (Invoices, Orders)

Optimistic creation for list views — append a placeholder record immediately with a `pending` status indicator, replace with server response on success, remove on failure:

```js
// ✅ OPTIMISTIC CREATE
const handleSubmit = async (formData) => {
  const tempId = `temp_${Date.now()}`;
  const placeholder = { ...formData, _id: tempId, _pending: true };

  setInvoices(prev => [placeholder, ...prev]);   // ← instant list update

  try {
    const response = await apiService.createDealerInvoice(formData);
    setInvoices(prev => prev.map(i => i._id === tempId ? response.invoice : i)); // swap placeholder
  } catch (err) {
    setInvoices(prev => prev.filter(i => i._id !== tempId)); // remove placeholder
    toast.error(`Create failed: ${err.message}`);
  }
};
```

**Note**: Do NOT apply optimistic create for invoices that trigger financial side-effects (stock deduction, ledger entries) server-side — partial rollback on the client with a committed server record creates a confusing diverged state. Use a loading indicator for these but keep the UX message brief ("Saving…").

### Visible Rollback Requirements

Any component converted to optimistic updates **must** include:
1. A `toast.error()` (or equivalent) explaining what happened and that changes were reverted
2. The previous state snapshot taken **before** the optimistic update, not after
3. For delete operations: re-insert the deleted item at its original index (not just push to end) — snapshot `[...items]` preserves order

```js
export const getAllBrands = async (req, res) => {
```

```js
export const createBrand = async (req, res) => {

```

App Performance

5 copy-paste prompts to fix the speed problems your AI coding agent left behind.


Why this exists

If an AI coding agent wrote most of your app, there's a good chance it works — and is quietly slow. These aren't bugs. They're defaults. No agent optimizes for scale unless you tell it to.

Below are 5 prompts for the 5 most common performance gaps. Copy them into Claude Code, Codex, Cursor, or whatever agent you're using. Run them one at a time, and test your app after each one before moving to the next.

01  Compress API responses in transit

“Check whether my API responses are compressed in transit. Enable gzip or brotli compression on the server or edge for JSON and text responses above a small size threshold, and confirm the client negotiates it via Accept-Encoding. Avoid double-compressing already-compressed payloads. Verify response transfer sizes drop significantly and responses still parse correctly on the client.”

02  Batch inserts and updates

“Find code that performs many individual INSERT or UPDATE statements in a loop where a single batched operation would work. Replace them with bulk/batched writes (multi-row inserts, batch updates, or a single statement) inside an appropriate transaction. Chunk very large batches to avoid oversized statements or long locks. Verify write-heavy operations complete far faster with fewer round trips.”

03  Add a circuit breaker for slow dependencies

“Identify external dependencies whose slowness or failures could cascade into my app, exhausting threads or connections while everyone waits. Add a circuit breaker that trips when a dependency is failing or too slow, fast-failing or serving a fallback until it recovers, with timeouts and limited concurrency to that dependency. Verify that a degraded dependency no longer drags down unrelated parts of the app and recovers cleanly.”

04  Apply optimistic UI updates

“Identify user actions (likes, toggles, adds, edits, deletes) that currently wait for the server response before updating the screen. Make them optimistic: update the UI immediately as if the action succeeded, then reconcile with the server result and roll back gracefully if it fails. Include clear error handling and a visible rollback so users aren't misled. Verify the happy path feels instant and failures restore the correct state.”

05  Cache rendered pages or fragments

“Find server-rendered pages or fragments whose output is identical (or nearly so) across many users and changes infrequently. Cache the rendered output and serve it directly, regenerating on a schedule or on content change, while keeping personalized regions dynamic via holes or client-side hydration. Ensure cache keys account for meaningful variations like locale. Verify these pages serve much faster and rendering load decreases.”
